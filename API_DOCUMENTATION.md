# API Documentation: Interactive Diagnostic System

This document provides all the necessary information for an AI agent or developer to build a user interface that interacts with the Interactive Diagnostic API.

## 1. Overview

This API provides access to a sophisticated interactive diagnostic engine. The goal is to determine the most likely diseases a user might have based on their symptoms. The process is conversational, involving a series of questions and answers.

The API is stateful, meaning it tracks the progress of each diagnostic session. A unique `session_id` is generated at the start of a session and must be used in all subsequent requests for that session.

## 2. Base URL & OpenAPI Specification

*   **Base URL**: `http://127.0.0.1:8000`
*   **Authentication**: None required.

A full, machine-readable OpenAPI 3.0 specification is automatically generated by the FastAPI server. This is the primary source for data models and endpoint definitions.

*   **Swagger UI (Interactive Docs)**: [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs)
*   **OpenAPI JSON**: [http://127.0.0.1:8000/openapi.json](http://127.0.0.1:8000/openapi.json)

## 3. Core Concepts

### Session Management
Each diagnostic conversation is a "session". A session is initiated via the `/start` endpoint. The `session_id` returned from this endpoint must be stored and included in all subsequent API calls for that diagnosis.

### Symptom Formatting
**This is a critical detail.** The symptom names used within the system's knowledge base use underscores (`_`) instead of spaces (e.g., `abdominal_pain`).

*   When the API returns a question like `"Do you have abdominal pain?"`, the UI must extract the symptom part ("abdominal pain").
*   When sending this symptom back to the `/answer` endpoint, it **must** be formatted with underscores.

**Example**:
- Question received: `"Do you have skin rash?"`
- Symptom to send: `"skin_rash"`

## 4. Diagnostic Workflow: A Step-by-Step Tutorial

This is the standard flow for conducting a diagnosis from a user interface.

### Step 1: Start the Session
- **Goal**: Begin a new diagnosis and get the first question.
- **Action**: Call `POST /start`.
- **Result**: You receive a `session_id` and the first `question`.
- **UI Action**: Store the `session_id`. Display the `question` to the user (e.g., "Do you have itching?").

### Step 2 (Optional): Free-Text Input
- **Goal**: Allow the user to describe their symptoms in their own words at the beginning.
- **Action**: Collect the user's text. Call `POST /describe` with the `session_id` and the `text`.
- **Result**: You receive the symptoms the API understood (`parsed_symptoms`), the current disease probabilities (`top_diseases`), and the next `question`.
- **UI Action**: Display the new `question` and update the list of possible diseases shown to the user.

### Step 3: The Question & Answer Loop
- **Goal**: Iteratively narrow down the diagnosis.
- **Action**: For the current question, get the user's answer (Yes/No/Unknown). Call `POST /answer` with the `session_id`, the formatted `symptom` name (e.g., "skin_rash"), and the user's `answer` (as an integer: `1` for Yes, `0` for No, `-1` for Unknown).
- **Result**: The API returns the next `question`, updated `top_diseases`, and a boolean flag `is_finished`.
- **UI Action**:
    1. Update the list of possible diseases (`top_diseases`) displayed to the user.
    2. Check the `is_finished` flag.
    3. If `is_finished` is `false`, display the new `question`.
    4. If `is_finished` is `true`, proceed to Step 4.

### Step 4: Finish the Diagnosis
- **Goal**: The session has concluded.
- **Result**: The `is_finished` flag is `true`. The `finish_reason` field explains why the session ended (e.g., confidence threshold reached, max questions asked).
- **UI Action**: Display the final `top_diseases` as the diagnostic result. Show the `finish_reason` to the user.

## 5. Endpoint Reference

### `POST /start`
Starts a new diagnostic session.

*   **Request Body**: None
*   **Response (`200 OK`)**:
    ```json
    {
      "session_id": "string (uuid)",
      "question": "string",
      "ig": "number (float)"
    }
    ```
*   **Example `curl`**:
    ```bash
    curl -X POST "http://127.0.0.1:8000/start"
    ```

### `POST /describe`
Processes a free-text description of symptoms for an existing session.

*   **Request Body**:
    ```json
    {
      "session_id": "string",
      "text": "string"
    }
    ```
*   **Response (`200 OK`)**:
    ```json
    {
      "parsed_symptoms": {
        "symptom_name_with_underscores": 1
      },
      "top_diseases": [
        [ "string (disease_name)", "number (probability)" ]
      ],
      "question": "string",
      "ig": "number (float)"
    }
    ```
*   **Example `curl`**:
    ```bash
    curl -X POST "http://127.0.0.1:8000/describe" -H "Content-Type: application/json" -d '{"session_id": "your-session-id", "text": "I have a fever and a cough."}'
    ```

### `POST /answer`
Submits an answer to a symptom question and gets the next step.

*   **Request Body**:
    ```json
    {
      "session_id": "string",
      "symptom": "string (formatted with underscores)",
      "answer": "integer (1, 0, or -1)"
    }
    ```
*   **Response (`200 OK`)**:
    ```json
    {
      "question": "string | null",
      "ig": "number (float) | null",
      "top_diseases": [
        [ "string (disease_name)", "number (probability)" ]
      ],
      "is_finished": "boolean",
      "finish_reason": "string | null"
    }
    ```
*   **Example `curl`**:
    ```bash
    curl -X POST "http://127.0.0.1:8000/answer" -H "Content-Type: application/json" -d '{"session_id": "your-session-id", "symptom": "fever", "answer": 1}'
    ```

## 6. Error Handling

The API uses standard HTTP status codes for errors.

*   `404 Not Found`: The provided `session_id` does not exist. The UI should prompt the user to start a new session.
*   `400 Bad Request`: The user's answer violates a logical constraint (e.g., reporting two mutually exclusive symptoms). The UI should inform the user of the conflict and potentially revert the last answer.
*   `422 Unprocessable Entity`: The request body is malformed (e.g., wrong data types). This should not happen if the UI is correctly implemented.
*   `500 Internal Server Error`: An unexpected error occurred on the server.
